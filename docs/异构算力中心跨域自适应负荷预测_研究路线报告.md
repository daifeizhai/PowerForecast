# 面向异构不完备数据的算力中心跨域自适应负荷预测——研究路线报告

> **研究定位**：用不同来源、不同计量层级、缺少部分特征的数据，学习可迁移的负荷规律，让模型在**未见过的计算设备、机架或数据中心**上仍能准确预测。  
> **状态**：研究设计稿（2026-10-24）；数据集信息已核对公开说明，实际可用天数、缺失率及计量边界仍需下载审计。

## 1. 研究要解决什么问题？

**一句话：** 算力中心之间差异很大，直接迁移预测模型常常失效；我们要让模型学会**“哪些规律可以共享、哪些不能迁移、共享多少”**。

| 现实困难 | 传统做法的问题 | 本课题的突破方向 |
|---|---|---|
| 不同中心设备与业务不同 | 在A中心准确，到B中心可能失效 | 学习跨中心共享的负荷变化规律 |
| 数据类型、单位和监测范围不一致 | 硬拼接数据会混淆物理意义 | 保留数据来源、计量层级和缺失信息 |
| 更多外部数据未必有用 | 无差别联合训练可能产生**负迁移** | 识别可靠来源，动态选择迁移知识 |
| 新中心只有很少的历史数据 | 从零训练效果有限 | 验证**零样本/少样本**跨域预测 |

**论文主线：** 发现跨域失效现象 → 分析失效原因 → 设计选择性迁移机制 → 证明在新域上更准、更稳。

## 2. 拟采用的方法与创新点

**暂定方法名称：** HAST（Heterogeneity-Aware Selective Transfer，异构性感知选择性迁移）。

| 模块 | 通俗理解 | 拟研究的作用 |
|---|---|---|
| ① 异构输入适配 | 先搞清楚“这是什么数据”，再喂给模型 | 统一时间接口；保留`W/kW/功率利用率`、节点/机架/设施、缺失特征标记；不能将不同标签硬凑成设施总功率 |
| ② 共享规律与本地差异分离 | 把“曲线怎么变”与“功率有多大”分开 | 学习周期、趋势、波动等共享动态，再通过目标域历史恢复实际尺度 |
| **③ 迁移可靠性门控（核心创新候选）** | 不让不相似的中心“乱教”新中心 | 用目标域**起报前的历史**、预测时长、源域相似度，选择预测专家；不可靠时回退保守预测 |
| ④ 留一域模拟训练 | 训练时反复假装遇到陌生中心 | 在源域之间轮流做“未见域”实验，让门控机制学习避免负迁移 |

**简化流程：** 多源数据 → 数据类型/计量边界检查 → 共享时序编码器 → 源域专家库 → 选择性迁移门控 → 未来功率曲线。

**创新性边界：** 归一化、Transformer、混合专家、迁移学习都不是新概念。论文须把贡献落实到**“如何在特征不齐、源域质量不同的条件下估计迁移可靠性，并降低负迁移”**，通过严格消融证明有效。

## 3. 推荐数据集（按研究价值排序）

| 数据集与入口 | 有什么 | 用于哪项实验 | 注意事项 / 推荐级别 |
|---|---|---|---|
| **[NLR ESIF设施功率与PUE](https://data.nlr.gov/submissions/300)** | IT、制冷、HVAC、泵、照明功率及室外温湿度；分项为kW | **设施级预测主验证候选**；环境/工况迁移 | 需核对采样间隔、连续天数与分项覆盖；**未见独立总表字段**，总功率须依公开定义核验后派生。**★★★** |
| **[NLR Eagle节点功率](https://data.nlr.gov/submissions/288)** + [GPU节点指标](https://data.nlr.gov/submissions/301) + [作业记录](https://data.nlr.gov/submissions/295) | 约2000节点；1分钟**瞬时**功率W；6个GPU节点的运行指标；约1380万条作业记录 | **跨节点/跨机架泛化主实验**，研究任务—功率关系 | 分钟瞬时样本平均只能近似15分钟区间平均；未覆盖设备不可假装已计入设施总负荷。**★★★** |
| **[云数据中心实测集（UCC 2023）](https://zenodo.org/records/10069402)** | 两组服务器共144台，约5—9个月，每10分钟记录功率、CPU等，部分有温度/风扇 | **跨服务器型号、跨集群迁移** | 10分钟改为15分钟须声明重聚合假设，不能称作原生15分钟实测。**★★★** |
| **[M100 ExaData 15分钟汇总](https://zenodo.org/records/7541722)** | 980+计算节点的CPU功率、温度、GPU及调度等指标；机架分包约24.8GB | 跨机架、多变量、不同运行状态验证 | 先核查具体功率列所覆盖的硬件边界，不能将CPU功率当整机功率。**★★★** |
| **[Marconi A2 / HazardNet](https://zenodo.org/records/10050368)** | 3312节点，2019年功率及进/出风温度 | 大规模跨节点、散热差异实验 | 需核实时间采样与连续率；不是设施总表。**★★** |
| **[Google PowerData 2019](https://github.com/google/cluster-data/blob/master/PowerData2019.md)** | 57个电力域，2019年5月的**功率利用信息** | 跨电力域泛化；归一化负荷形态学习 | 不能不经量纲核对就视为kW；只有约1个月。**★★** |
| **[Alibaba GPU v2020](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2020/README.md)** | 2020年7—8月训练/推理任务、资源请求及利用信息，约1800台机器 | **可选**任务行为表征预训练 | 无可直接监督的真实功率标签；生命周期统计值不能泄漏未来。**★★** |
| **[PM100作业功耗](https://zenodo.org/records/10127767)** | Marconi100约23.1万条作业、节点/CPU/内存层面作业功耗 | 任务级功耗规律辅助学习 | 按作业记录，非连续15分钟设施负荷。**★** |
| **[INL C3数据中心小时用电](https://nrds.inl.gov/dataset/c3_datacenter_hourly_power_usage)** | 2020年7月—2026年1月，小时用电记录 | 长周期、跨设施**小时级辅助验证** | **不能用于原生15分钟预测真值评价**。**★** |

**建议首批只选3组：NLR设施功率 + NLR节点功率 + 144台服务器数据。** Google和M100在第二轮加入；Alibaba可在主模型成立后再做，**不是必须凑齐的组件**。

> **重要区别：** 多个NLR机架 ≠ 多个独立数据中心。若尚无多个**可比计量边界的设施总功率**数据集，论文可以严谨证明“跨节点/跨机架/跨集群泛化”，但不应直接宣称已经充分验证“跨设施总表泛化”。

## 4. 实验计划（先验证问题，再设计模型）

| 步骤 | 做什么 | 应得到什么 |
|---|---|---|
| **第1步：数据审计** | 整理单位、计量层级、时间跨度、缺失率、有效连续天数；统一接口 | 数据质量清单；明确每套数据能预测哪一级功率 |
| **第2步：寻找负迁移** | 每次留1个机架/服务器组作为未知目标；对比“仅目标域训练”“多源直接迁移”“多源联合训练” | **跨域MAPE矩阵、负迁移热力图**；确认问题真实存在。目标域单独训练是*有监督参考上界*，不与零样本结果混为同一数据条件 |
| **第3步：提出方法** | 加入共享/本地解耦、状态相似性、可靠性门控和保守回退 | HAST与去除各模块的消融结果 |
| **第4步：扩大验证** | 加入Google、M100；按原标签性质分别评价；设置特征缺失、来源增减、预测时长变化 | 验证异构性与适应性，做“数据越多是否越好”曲线 |
| **第5步：论文整理** | 报告均值、最差目标域、负迁移比例、参数稳定性与失败案例 | 可复现的实验表与完整科研叙事 |

**至少比较：** Seasonal Naive、LightGBM、DLinear、PatchTST/TCN、RevIN+预测器、多域联合训练、HAST及其消融版本。

**最关键的3张图：** ①源域—目标域迁移收益热力图；②增加异构源域后MAPE的变化；③不同预测时长下各迁移专家的权重及目标域误差。

## 5. 与当前项目任务如何对齐？

| 项目要求 | 执行约束 |
|---|---|
| 输出目标 | 优先预测**数据中心整体总有功功率kW**；节点级/利用率实验作为算法验证，单列报告，不能冒充设施总表指标 |
| 采样、历史、预测时长 | 15分钟；默认历史14天=1344点；预测4h/24h/3天/7天，分别为16/96/288/672点 |
| 核心指标 | **MAPE**优先，附WAPE、RMSE、MAE；95%目标对应真实设施总功率MAPE≤5%，非预设成果 |
| Google原有划分 | 24h开发：D14/16/18/20末起报；测试D22—30末起报。7天开发：D14/15末；测试D22/23/24末 |
| 泛化协议 | **零样本：**目标域不参与参数训练，仅用起报前历史做输入；**少样本：**允许明确标记的目标域训练段，须独立报告 |
| 防泄漏 | 不使用未来真实任务状态、温度、功率和跨越起报时点才计算出的统计信息；测试阶段按既定协议冻结权重 |

## 6. 现有PowerForecast架构需要重建吗？

**结论：不建议重新建项目，改动是“中等规模的增量扩展”。** 已有数据接入、窗口切分、基线模型、MAPE评价都应保留。

| 保留 | 建议新增（示意） |
|---|---|
| `configs/datasets/`、`src/data/`、`ForecastInputs`、`WindowBatch`、现有基线与测试协议 | `domain_id`、`target_scope`、`label_origin`、`feature_mask`等元信息；跨域采样器；`models/cross_domain/`；`experiments/leave_one_domain_out/` |
| 原先的单域训练与评价入口 | 在其外新增“多域训练 / 留一域测试”入口，不改老模型接口 |

**实施优先级：** 先补数据元信息和留一域实验；确认存在负迁移，再开发HAST。具体目录名可按实际仓库调整。

## 7. 论文可行性的两条底线

1. **优质训练数据不是每套都必须有，但真实评价标签不可少。** 实测、分项派生、参数估算、功率利用率分别编号与评价；IT功率、节点功率、设施功率边界不互换。
2. **创新必须经得起对比。** 共享表征、RevIN、MoE本身已有研究；应证明“选择性迁移机制在未见域上显著降低负迁移”，并报告何时失败。
